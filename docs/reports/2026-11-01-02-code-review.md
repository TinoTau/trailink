# 代码审查：重复、冗余与死代码

## 目标

整理前先通读后端（Controllers / Services，约 5600 行）和前端（约 9000 行），列出重复实现、违反 SSOT 的地方和死代码，作为下一轮重构的清单。本轮只读，不改代码。

## 结论

没有发现平行的订单系统、第二套表或第二套 API。主要问题集中在三类：

1. **同一条业务规则在后端写了好几遍**：派出人、拆单、「今天」。
2. **同一段机制在前端复制了一份**：照片查看器、照片压缩、置顶图标。
3. **两个大页面承担了太多职责**：`DispatcherPage.tsx` 2721 行，48 个 state、49 个 ref；`VehicleBoard.tsx` 942 行。

## 三、前后端重复的业务规则（需要你决定）

以下规则在前端和后端各算一遍，是真正的「两个事实来源」。

| 规则 | 后端 | 前端 |
|------|------|------|
| 拆单 | `CanClearAssignment`、`VehicleOrderSplit` | `orderFlags.isSplitOrder` |
| 历史单（已派完且已结束） | `CompanyDeskController` 查询 | `orderFlags.isHistoricalOrder` |
| 冲突订单（同一司导同一天） | `OrderScheduling.FindDriverConflictsAsync` | `orderFlags.conflictingOrderIds` |
| 订单显示名（公司订单号 → 共用备注） | `OrderScheduling.FirstLine` 拼的冲突提示 | `orderFlags.orderDisplayLabel` |

彻底消除的办法，是由后端在订单列表里直接返回 `isSplit`、`isHistorical`、`hasConflict`，前端只负责显示。但这会改 API 契约，而且线上要同时发布前端和后端。
