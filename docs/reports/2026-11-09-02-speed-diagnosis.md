# 网页慢的原因排查 2026-11-09

## 问题

网页加载大约要 3 秒。站点没有并发，数据也很少，这不正常。要确认是网络延迟还是数据库查询。

## 结论

- 主要是网络延迟，不是数据库查询。
- 另外，服务器偶尔会卡几秒，像是 1GB 内存的小机器在用交换空间，或者 CPU 被限流。这一点要在服务器上跑诊断脚本确认。

## 测量

### 1. 线上（在本机的 Claude 内置浏览器里打开 trailink.cc，读浏览器记录的每个请求的耗时）

- 每个请求至少约 210ms，静态文件和不查库的接口都一样（favicon 218–315ms，未登录的 `/api/auth/me` 约 212ms）。这就是新西兰到服务器所在地（us-west1，俄勒冈）一来一回的时间。
- 第一次打开首页用了 2.6 秒，其中：
  - 建连接 740ms（其中 TLS 533ms）；
  - 等首页 523ms；
  - 主程序 JS 传输约 1.1 秒（压缩后 313KB，解压后 944KB）；
  - 之后再请求 `/api/auth/me`。
  - 登录后，调度台还要并行请求订单、司导、车辆、抢单，再请求司导行程，每一层至少再加约 210ms，加起来就是用户感到的 3 秒左右。
- 偶发的长时间卡顿：
  - 页面刚打开时 `/api/auth/me` 等了 4.3 秒；
  - 随后一次 `/api/health` 等了 7 秒。
  - 这两个请求在服务器上几乎不做事，正常时都约 210ms。
  - 隔 5、15、30、60 秒再请求，没再出现，最多 451ms。
- 服务器已开 gzip，但静态文件没有长期缓存头（只有 ETag），每次打开都要再问一次服务器。

### 2. 本地（同一套代码，60 张单、240 个行程日、6 位司导）

- 各接口耗时（毫秒，连续 6 次）：

  | 接口 | 耗时 |
  |---|---|
  | `/api/auth/me` | 4–6 |
  | `/api/orders?desk=true` | 31–48（第一次 110） |
  | `/api/drivers` | 6–9 |
  | `/api/vehicles` | 4–6 |
  | `/api/grab/claims` | 6 |
  | `/api/company` | 16–19 |
  | `/api/grab` | 93–190（最慢，但也不到 0.2 秒） |

- 本地日志里 3952 条数据库语句：中位 1ms，95% 在 2ms 以内。超过 1 秒的只有接口刚启动时的 2 条（冷启动）。

## 需要在服务器上确认的（脚本只读）

- `release/diagnose-speed-20261109.sh`：
  - 不连接数据库、不改配置、不重启容器；
  - 看内存、交换空间、vmstat（si/so、st）、内存与 CPU 压力、各容器占用和是否被 OOM 杀过；
  - 在服务器本机请求 health、auth/me、首页（排除新西兰到美国的网络）；
  - 从 api 日志统计过去 24 小时数据库语句耗时，列出最慢的 10 条；
  - 结果写到 `~/trailink-speed-20261109.txt`。
- 统计语句耗时的部分已用本地日志验证（日志里超过 1000ms 写作 `1,193ms`，脚本已处理）。

## 可以做的改进（未实施，等确认）

1. 服务器挪到离新西兰近的地区（如 australia-southeast1 悉尼，单程延迟约 30–40ms）。每个来回从约 210ms 降到约 40ms，效果最大。注意免费的 e2-micro 只在美国地区。
2. 不挪服务器：前面加 Cloudflare（免费）。HTTPS 连接在澳新就近建立，静态文件就近缓存，第一次打开能省下大约 1 秒以上；接口仍然要到美国。
3. Caddy 给 `/assets/*`（文件名带哈希）加 `Cache-Control: public, max-age=31536000, immutable`，第二次打开不用再下载、也不用再问服务器。
4. 主程序 JS 944KB，可以按页面拆分（登录页不加载调度台代码）。
5. 如果诊断确认是内存不够：
   - 给 Postgres 和 api 限内存；
   - 或者换 e2-small（2GB）；
   - 或者把 EF 的 SQL 日志降为 Warning，少写日志。
