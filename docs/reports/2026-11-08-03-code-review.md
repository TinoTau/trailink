## 已修：派给调度里放出去的单，抢了以后没人能确认（今天引入的回归）

1. 问题：
   - 公司账户在派给调度里，把一张还没分调度员的单设成「公司内部 / 面向所有人」，司导就能抢。
   - 但今天改过的「待确认抢单」只列自己调度台上的单，这张单不在任何人的调度台上，抢单记录谁也看不到、也没人能确认。
   - 按用户的决定修复：这种单直接分给公司账户自己，由公司账户当调度员来管理。
   - `PUT /share-level`：公司账户把没分调度员的单改成 1 或 2 时，`assigned_dispatcher_user_id` 写成公司账户。
   - `OrderRules.OnDesk` / `IsOnDesk`：公司账户的调度台另外带上「没分调度员、但已经放出去」的本公司旧单。以前放出去的单不用改数据，也能在公司账户的调度台上看到、确认。
   - 待确认抢单改用和调度台订单列表同一条 `OnDesk` 规则（子查询），不再单独写一套。
   - 新测试 `Company_releasing_a_pool_order_takes_it_onto_its_own_desk`：
     - 派给调度里建的单放出去后，分给了公司账户自己，出现在调度台；
     - 司导抢后，公司账户的待确认里有这条抢单，并能确认。

## 记录，暂不改

3. 改日期把原来的各天「按顺序」排成连续日期。原来中间有空档的单（例如删过中间一天），改完空档会被挤掉。界面提示里写了「按顺序搬过去」。
4. 改日期没有限制不能改到今天以前，方便补录已经发生的单。如果要禁止，在 `OrderReschedule.Validate` 里加一行。
5. 改日期时，删掉末尾几天的电子票文件是在写库之前删的。写库失败的话，文件已经没了（概率很低，和原有删除订单的写法一致）。
6. 改日期的冲突检查和保存不在同一个事务里。两个人同时把同一位司导派到同一天，仍可能同时成功（和原有派单逻辑一样，靠 `hasDriverConflict` 标红兜底）。
7. 编辑、关闭按钮的点按范围是 44px，用负边距贴回原行高。紧挨着按钮点下面一行的文字时，可能点到按钮。手机浏览器本来也会把附近的点按吸附到按钮上。
8. 测试偶发：
   - `GrabTests`（以前就有）偶发失败；
   - 今天第一次见 `FileUploadTests.Tickets_and_screenshots_leave_one_week_after_the_order_ends` 在全量并行时失败一次。
   - 两者单独重跑都过，连跑 3 次全量都过。原因未查。

## 看过、没有问题的

- 权限：
  - `PUT /dates`：公司限本公司；公司的单限分到它的调度员；自留单限建单人。
  - `DELETE`：调度台只处理自己调度台上的单；派给调度只删本公司的单，补上了原来能删别家公司订单的漏洞。
  - `DELETE /api/dispatchers/drivers/{id}`：只删自己名下的批准记录。
- `OnDesk` 是表达式（查库用），`IsOnDesk` 是同一条规则的内存版。用到 `IsOnDesk` 的地方都已带上行程日。
- 活动时间平移用 `AddDays`，时间按当地时间存，不受夏令时影响。
- 前端：
  - 调度台用 `?desk=true` 取单；
  - 建单、AI 建单带 `onMyDesk`；
  - 删除 / 退回按 `assignDesk` 判断，不再看角色。
- 透明度共用一份 `useCalendarInk`。点订单日期打开司导时，跳过已隐藏的司导。
- 没有新增数据库结构，也没有改已有数据。
