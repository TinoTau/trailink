# Trailink V1 开发计划

版本：V1 MVP 第一阶段  
日期：2026-10-23

本计划只覆盖第一阶段可运行核心功能。未经批准不得扩大业务范围、创建收费 AWS 资源或进行生产部署。

---

## Phase 1 — 基础工程

任务：

- 创建 Git 项目结构
- 创建 ASP.NET Core Web API
- 创建 React + TypeScript 前端
- 配置 PostgreSQL
- 配置 EF Core
- 创建数据库迁移
- 配置 Docker Compose
- 建立本地开发环境

验收：

- 后端能够启动
- 前端能够启动
- 数据库能够连接
- Migration 能够执行
- Swagger / OpenAPI 能够访问
- `/openapi/v1.json` 为前端 API transport types 的唯一来源，`npm run api:types` 生成 `frontend/src/api/generated/`

---

## Phase 2 — CRUD

任务：

- Drivers CRUD
- Orders CRUD
- Itinerary Days CRUD
- Order Files CRUD
- S3 文件存储接口

验收：

- 能创建、查询、修改和删除司机
- 能创建多日订单
- 能修改每日行程
- 能上传和查看原始订单附件

本地开发可使用 S3 兼容的本地测试存储或可替换的文件存储配置，不得要求开发者一开始就创建正式 AWS 资源。

---

## Phase 3 — 派单

任务：

- 整单派单
- 单日派单
- 修改司机
- 清空司机
- 简单日期冲突提示

验收：

- 一个三日订单可以全部分配给同一司机
- 可以将第三天修改为另一名司机
- 数据库直接更新 `driver_id`
- 不生成任何派单历史记录

---

## Phase 4 — 日历与部署准备

任务：

- 订单日历
- 司机日历筛选
- 手机端响应式适配
- 基础 API 测试
- Docker 构建
- AWS 部署配置和说明

验收：

- 可以按月份查看行程
- 可以筛选司机
- 可以点击日期查看行程详情
- 前后端可以通过 Docker 构建
- 提供 AWS 部署说明和预计资源成本

第一阶段不要求在未经批准的情况下直接部署收费 AWS 资源。

---

## 质量要求

必须：

- 保持代码简单易读
- 使用清晰的英文命名
- API DTO 与数据库实体适度分离；前端不手写重复 DTO，页面权限与菜单只读统一导航配置
- 使用 EF Core Migrations
- 处理基本输入错误
- 使用异步数据库访问
- 避免 SQL 注入
- 保护数据库连接字符串和 AWS 密钥
- 不将真实密钥提交到 Git
- 为核心 CRUD、派单和日历查询编写基础自动化测试
- 提供 README 启动说明

不要求：

- 100% 测试覆盖率
- 复杂测试基础设施
- 多层接口抽象
- 高并发性能优化
- 分布式架构
- 自动化运维平台

---

## 当前进度

已完成：

- 目标框架 net10.0，SDK 10.0.402（`global.json` 锁定）
- 本地 Docker PostgreSQL 16
- 司机 CRUD
- 订单 / 每日行程 / 活动项目 CRUD
- 整单与按天派单（只写 `itinerary_days.driver_id`）
- 订单在调度台与本人行程里编辑，不另开 `/orders` 列表页
- 司机端连续滚动日历；公司、调度员、司导登录后都看本人行程，已结束的单也留在日历上
- 司机日历与调度台共用订单 / 司导列表；有行程日期框与调度台司导日历共用 `CalendarDayCaption` 展示派出人，我的行程在已绑公司时连上公司名，过长则用本人的公司缩写；点日期展开的订单信息与调度台订单卡同一套 `OrderInfoFields` / `updateOrderInfo`，备注分 `order_notes`（调度员各人一条）/ `orders.driver_notes`；领取、框选建稿、取消只写 `itinerary_days.driver_id`；领取已绑公司真实订单时覆盖并删除本人占位单
- 切换到调度台、派给调度、我的行程、公司信息或个人信息，以及从其他窗口回到当前页时，重新读取该页数据；未保存的输入保留
- 调度台：创建订单与司导同一套框选建单、筛选项为未分配/所有订单（未分配含过期仍有空日期的单；所有订单不含已派完且已结束的历史单）、已分配颜色仅在所有订单且按用户写入 `users.assigned_color`、卡片日历标出当天、两卡同时打开时订单日历按月带动司导日历、订单卡已绑公司时调度员退回公司池、未绑公司或公司账户才真删、订单信息保存后回日历、当日行程独立卡片、整单/按天拖拽派单、点开司导时日历包含这位司导的全部未来行程，不限本公司，只有自己派出的日期写姓名；从司导卡片拖一天到订单区取消（仅自己分配的单；多分配人/多司导/未派完按拆单取消当天、同一人整单才整单解绑；我的行程取消本人行程不看分配人）、司导图标下方优先显示当前调度员自己的备注（互不可见）、无备注才显示姓名，置顶在图标上（localStorage），隐藏写 `driver_notes.hidden`，移除在卡片备注旁，冲突拒绝写入（已绑公司的真实订单可覆盖并删除司导自建未绑公司占位单）；公司信息页：公司账户只看已派完且已结束的历史单；司导看自己当前接的单，调度员看自己当前接的和分配的单，已结束和尚未结束都在内，分配变化后不再显示
- 公司派给调度：`orders.assigned_dispatcher_user_id` + `PUT /api/orders/{id}/dispatcher`，页面复用 `/company/assign` 的调度台，只整单、同时只一位调度员；点调度员是订单池（未完成 / 已完成），可以排序、置顶和隐藏；隐藏写 `dispatcher_notes.hidden`；解除绑定走现有删除成员，不能解除公司账户自己，未完成订单退回公司池；点订单日历标司导；公司给调度员的备注写 `dispatcher_notes`
- Cookie 登录与三类角色；公司表；申请成为调度员由公司批准，批准前公司名单和派给调度都看不到；申请成为司导由该调度员批准，批准前他的调度台看不到，同公司其他调度员也不共享；批准后写入 `company_members`，并保留 `driver_applications.approved_at`；调度员可删除自己这一行来解除绑定；未完成订单里分给这位司导的日期按天收回，已结束的行程保留。第一次点垃圾桶只给垃圾桶套上红框，再点一次才解除，不弹框；公司账户或该公司调度员把公司订单派给有账号的司导时，若还不是成员则写入 `company_members.role=driver`，这不进入公司账户的调度台；公司调度台只看向本公司账户申请并已批准的 `driver_applications`，其中包含注册时自动批准的自指行，旧账号在登录或 `me` 时补上，不能解除自己的司导身份；批准前不显示别人，也没有隐藏记录；公司信息页只有公司账户能看到批准/移除调度员
- 个人信息可改自己的 `users.name`（`PUT /api/auth/name`）、联系方式（`PUT /api/auth/contact`，写 `users.contact`）、登录用户名（`PUT /api/auth/username`）和登录密码（`PUT /api/auth/password`，须验证当前密码；页面用明文输入当前密码和新密码）；有本人 `driver_id` 时同步 `drivers.name`，调度台司导卡读 `GET /api/drivers` 时优先显示账号姓名。调度台司导详情、公司信息的待批准申请、个人信息的司导申请，以及我的行程点开日期后公司订单号下的调度员姓名旁，都读 `users.contact`
- 本地演示数据：`dotnet run -- --seed-demo`（密码均为 `Passw0rd!`）
- 清空业务表：`dotnet run -- --wipe-data`（含 `driver_notes`，不写入演示数据）
- 只清空订单、行程、活动和订单附件记录：`dotnet run -- --wipe-orders`，用户和公司保留
- 统一本地文件存储：二维码、头像、电子票、订单截图，根目录 `App_Data/files/`
- 公司建单绑定本公司；调度员和司导建单都不默认绑所属公司，即使只属于一家；调度员须搜索并点选后立即绑定或改绑 `orders.company_id`；公司 `GET /api/orders` 只看绑到自己的单
